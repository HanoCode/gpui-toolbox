# 项目管理：与 `temp/devAssistant` 的功能与布局差距分析

> 生成日期：2026-10-17。方法：逐文件核对本方 `crates/duck-project`（7.8k 行）+
> `crates/duck-app/src/pages/projects`（27.6k 行）与参考实现 `temp/devAssistant/src`
> （任务域约 20.5k 行），结论全部附 `文件:行` 证据；与 `docs/projects-design.md`
> 冲突处以**代码实测**为准。
>
> 读法：§1 定坐标（两边不是同一类产品），§2 逐层看布局，§3 是差距清单（带评级），
> §4 是像素级规格差，§5 是**本方领先项**（不要为了对齐而丢），§6 是落地顺序。

## 0. 总览

| 维度 | 参考 `devAssistant` | 本方 `projects` | 判定 |
| --- | --- | --- | --- |
| 数据模型 | 扁平任务（无项目/分组） | 分组 → 项目 → 任务 → 子任务 / 里程碑 | 本方强（结构治理） |
| 任务状态 | 5 态（todo/active/done/deferred/cancelled） | 6 态（+blocked） | 本方强（阻塞可表达） |
| 视图 | 看板（唯一）+ 独立日历窗 | 看板 / 列表 / 日历 / 时间线 / 报表 / 日志 / 归档 | 本方强 |
| 单任务执行 | 卡片内动作 + 番茄钟 + 分心检测 + 专注报表 | 菜单动作 + 手填工时 | **参考强（最大缺口）** |
| 捕获 | 独立快速任务窗（**全局键只有文档、代码里没注册**） | 页内 Spotlight + 浮窗一行新建（**浮窗不解析记号**） | 各有半成品；本仓离得近（§8.2） |
| 复盘 | 4 类图表 + 6 tab 报表 + 通知中心（定时日报/周报） | KPI + 柱状 + 条形 + 导出；通知在 shell 层 | 各有强弱 |
| 布局骨架 | 页面式（header → 筛选卡 → 三列 grid） | 三栏 shell（左树 / 主区 / 右详情 + 状态栏） | 本方强（信息密度） |
| 治理 | 无归档、无撤销、无批量、无导入导出 | 归档中心 / 撤销栈 / 批量 / 导入导出 / 周计划 | 本方强 |

差距计数：**P0 5 项 · P1 9 项 · P2 9 项**（§3，界面与功能层）；另有 **§8 操作流程层**（13 条通路 + 步数账本），两层的 P0 不重叠。

一句话结论：**结构与治理已超参考，差距集中在「一张卡从被看见到被推进」的那 5 秒**——
动作入口、计时闭环、筛选反馈、看板落位、详情信息完整度；流程层则集中在**同一个意图有四条路径、后果各不相同**。

## 1. 先定坐标：两边的心智模型不同

```
参考 devAssistant（扁平任务，页面式）
┌──────────────────────────────────────────────────────────┐
│ 任务看板   [新建][导入][刷新][悬浮窗][日历][AI 预测]      │
│ ┌──────────────────────────────────────────────────────┐ │
│ │ 四象限 ▾   标签（多选）▾   重置   筛选结果 12 个任务  │ │
│ └──────────────────────────────────────────────────────┘ │
│ ┌─待办(1fr)─┐ ┌─进行中(1fr)─┐ ┌─已完成(1fr)─┐            │
│ │ 卡片      │ │ 卡片        │ │ 卡片        │  gap 24    │
│ │ └延后 N 条 │ │             │ │             │            │
│ └───────────┘ └─────────────┘ └─────────────┘            │
└──────────────────────────────────────────────────────────┘
   任务 = 分类 + 优先级 + 四象限 + 标签 + 4 个日期 + 番茄钟

本方 projects（项目→任务，三栏 shell）
┌─────────────────────────────────────────────────────────────────────┐
│ 标题栏 40 · 搜索 · 窗口按钮                                          │
├────┬──────────────┬──────────────────────────────┬─────────────────┤
│活动│ 左栏 260     │ 工具条 34                    │ 右栏 300        │
│栏  │ 智能列表 4 档 │ [看板|列表|日历|时间线|报表|日志] │ 任务详情        │
│48  │ 项目树       │ 全部任务[N] ●Alpha[N] …      │ 属性（内联可改）│
│    │ 标签段       │ ⋯ 排序/分组/显示完成/导入导出 │ 进度（四档）    │
│    │ 归档中心     │                              │ 子任务/里程碑   │
│    │ 统计条       │ 视图内容（定宽列 268×N）     │ 上下文/备注     │
├────┴──────────────┴──────────────────────────────┴─────────────────┤
│ 状态栏 28 · 范围 · 本视图 N · 共 N · 完成 N · 逾期 N · 快捷键提示   │
└─────────────────────────────────────────────────────────────────────┘
```

**布局差距不是「谁更好看」，而是三处结构性选择不同**：

1. **筛选的位置**：参考把筛选做成主区顶部一张「筛选卡」（`TaskBoard.vue:41-101`），
   本方拆成「左栏智能列表 + 左栏标签 + 工具条范围 chips + 显示完成开关」四处
   （`view.rs:807`、`state.rs:584`）。前者的组合筛选一眼可见，后者更省纵向空间但
   **缺少「四象限 / 优先级 / 区间」这条轴，也缺少「筛完还剩几条」的反馈**。
2. **详情的位置**：参考是模态弹窗（`TaskDetailModal.vue:1-10`），本方是常驻右栏
   （`view.rs:4603`）。右栏适合「边看列表边改」，但**信息上限更小**：参考详情能放
   时间轴、Git 分支、里程碑内联表单，本方右栏只能放属性表 + 四档进度 + 里程碑只读列表。
3. **执行闭环的位置**：参考把「开始 / 暂停 / 完成」放在**卡片上**（`TaskCard.vue:87-89`），
   并把「开始」接到番茄钟（`TaskCard.vue:144-148`）。本方把动作收进菜单
   （`widgets/task_menu.rs:45-190`），「开始」只改状态、不计时。这决定了
   **从看到任务到动起来是 1 次点击还是 3 次点击**。

## 2. 布局逐层对照

### 2.1 壳层与导航

| 项 | 参考 | 本方 | 差距 |
| --- | --- | --- | --- |
| 导航 | 全局侧边栏（8 个页面平铺），任务页内无层级 | shell 活动栏 48 + 左栏 260（智能列表 / 项目树 / 标签 / 归档 / 统计条） | 本方多出**项目维度**，参考的任务页没有「范围」概念 |
| 左栏内容 | 无 | 4 档智能列表（带计数）+ 分组/项目（色点 + 未完成数）+ 标签（收藏优先、使用次数）+ 归档中心（徽标）+ 三格统计 | 参考无对应物；本方的左栏已经是「工作台」而非「导航」 |
| 右栏 | 无（详情靠弹窗） | 常驻 300，选中即显示，未选中显示「选中一张卡片查看详情」 | 右栏**没有项目态**：选中项目时右栏仍是空提示，项目里程碑无处可看（见 G-PRJ-8） |
| 状态栏 | 无 | 范围 / 本视图 N / 共 N / 完成 N / 逾期 N / 搜索词 + 快捷键提示（`view.rs:2192`） | 本方独有 |
| 响应式 | 900px 两列、768px 单列（`TaskBoard.vue:1918-1943`） | 定宽列 268 + `overflow_x_scroll`（`view.rs:2147`、`kanban_column.rs:26`） | 窄窗下参考重排、本方横向滚动；本方理由（列不随列数跳宽）成立，但**窗口 < 900 时体验明显更差** |

### 2.2 工具条

参考：页面标题 + 6 个动作按钮（新建 / 导入 / 刷新 / 悬浮窗 / 日历 / AI 预测，
`TaskBoard.vue:1-31`），**没有视图切换**（只有看板）。

本方：`segmented_tabs` 六档视图 + 分隔线 + 范围 chips（全部任务 + 每个项目）
+ 弹性占位 + 排序 / 分组 / 显示完成 + 分隔线 + 导入 / 导出 / 快速新建 / 新建
（`view.rs:807-830`）。

差距：
- 参考有「刷新 / 悬浮窗 / 日历窗」的**页面内开关**；本方浮窗与日历浮窗只有全局热键
  （`⌥⌘T` / `⌥⌘C`）与托盘，页面内无入口 → 用户不知道有这两个窗。
- 参考有「AI 预测」入口（本方明确不采纳，见 §5 说明）。
- 本方的「范围 chips」占了参考「筛选 chips」的位置：设计文档 §4.1 写的是
  「中：筛选 chips（今天/本周/逾期/P0-P1）」，实现改成了项目范围 chips
  （`view.rs:926`），四档日期口径挪进了左栏 → **工具条上没有一处能改「看什么」的筛选**。

### 2.3 看板网格与列

| 规格 | 参考 | 本方 |
| --- | --- | --- |
| 网格 | `grid-template-columns: repeat(3,1fr)`，gap 24（`TaskBoard.vue:1817-1824`） | `flex_row` + 定宽 268 + gap `spacing.sm` + 横向滚动（`kanban_column.rs:26`、`view.rs:2147`） |
| 列容器 | `card-bg` + 1px 边框 + 圆角 **20px** + padding **8px** + hover 边框变亮（`:1832-1852`） | `extended.colors.chrome` + 圆角 `components.card_radius` + 无 hover 变化 |
| 列头 | 8px 状态点 + 14px/700 标题 + 11px 胶囊计数（`monospace`）+ padding 12/8（`:1858-1885`） | 8px 色点 + `typography.sm` MEDIUM 标题 + `neutral_tag` 计数 + WIP 徽标（「WIP 5 / 超 WIP 2」）+ 列设置入口（`kanban_column.rs:117-171`） |
| 卡间距 | 12px（`:1892-1900`） | `spacing.xs`（4px 级） |
| 列内空态 | `n-empty`「暂无进行中的任务」，距顶 40px | 一行 `xs` 「拖一张卡片到这里」（`kanban_column.rs:180-200`） |
| 列底动作 | 虚线「+ 添加卡片」，hover 转实线 + 图标旋转 90°（`:1961-1990`） | 虚线「+ 添加任务」，hover 只变色（GPUI 无 transform） |
| 未落列状态 | `deferred` 折进「待办」列的**延后任务分区**（虚线分隔 + 独立计数 + 卡降透明度，`TaskBoard.vue:126-152`、`:1955-1975`） | **已对齐**：待办列底部一段可折叠的「已搁置 N」（`kanban_column.rs::deferred_section`），展开后卡片整体压暗一档（`opacity.dim`），与参考同一个心智；`cancelled` 仍不进看板（那是「决定不做」，摆回来会让人以为还有活） |

> **G-PRJ-2 的证据**：`ProjectStore` 的看板查询按列 `status_key` 取任务
> （`tasks_in_status(column.status_key)`），默认列只有 todo/doing/blocked/done；
> `deferred` 任务只有在用户手工建一列映射到它时才可见 —— **本轮已按参考的做法补上**
> 同列内分区（`state::deferred_tasks` + `deferred_open`，折叠时也留一行入口：
> 完全不给入口等于这些任务在界面上不存在）。⚠️ `movement_order()` 同步把展开后的
> 搁置卡并进 J/K 的行走顺序，否则它们看得见却选不中。

### 2.4 卡片

参考卡片（`TaskCard.vue:1-110`）：

```
┌───────────────────────────────────────┐
│ [分类Badge] [◫象限 24×24]  ●高 ⋯      │  ← 分类 + 象限徽标 + 优先级 pill(高24)
│ 任务标题（14px / 1.6 / 两行截断）      │
│ ▓▓▓▓▓▓░░░░░░ 45%                      │  ← 4px 进度条 + 11px 读数
│ [标签1][标签2][标签3] +2   [开始][完成]│  ← 标签 3 个 + N；卡内动作按钮
└───────────────────────────────────────┘
hover：translateY(-2px) + 阴影 + 白色扫光（:326-345）
```

本方卡片（`task_card.rs:1-30` 结构注记）：

```
┌───────────────────────────────────────┐
│ ┃ ●首标签 [Q2] ★            ⋯         │  ← 项目色点 + 仅首个标签 + 象限 + 置顶
│ ┃ 任务标题（sm 13/18 MEDIUM，自然换行）│
│ ┃ ▓▓▓▓░░░░ 45%（仅未完成）            │
│ ┗ P0 · 2/5 · 阻塞 · 📅10-18      45%  │  ← 元信息行，无动作按钮
└───────────────────────────────────────┘
hover：底色转 hover_tint + 边框转强调色（无位移）
```

差距（按影响排序）：

1. ~~**卡内无动作**~~ **已补**：卡片 `.ctop` 行末、`⋯` 之前给一个主行动 ——
   `todo` →「开始」、`doing` / `blocked` →「完成」（`task_card.rs::primary_action`），
   走 `page.set_task_status`（回执 / 撤销 / 广播都自动带上）。只给一个而不是三个：
   268 宽下再塞按钮就挤标题，完整动作组仍在 `⋯` 与右键菜单。
2. **标签只显示 1 个**（`task_card.rs:172-176`），参考 3 个 + `+N`（`:73-99`）。
   本方理由写在模块头第 4 条（其余在详情看），但在「一屏扫读」场景里 1 个标签
   等于没有标签。
3. **无分类/类型徽标**：参考用固定分类 Badge 承担「这是哪类活」；本方只有项目色点
   （无项目名）→ 需要**记住颜色**才能识别项目。这是「用项目替代分类」的代价，
   可以在色点后加项目名（`xs`，truncate）补齐。
4. **悬停无抬升 + 扫光**：GPUI `Div` 无 transform，仓内约定禁 `translateY`；
   属平台限制，不列为差距（§5 已记录），但**扫光层**可以用 `hover_tint` 渐变模拟，
   当前没做。
5. **标题不截断**：参考 `line-clamp:2`（`:437-447`），本方自然换行（模块头第 2 条）。
   268px 列下长标题会把卡片撑到 5–6 行，一屏能看的卡更少 → 建议给 2 行截断
   （GPUI 可用 `max_h` + `overflow_hidden` 近似，或按字符数截断 + tooltip）。

### 2.5 列表视图

参考**没有**列表视图（只有三列看板）。本方列表是 7 列（任务 / 项目 / 优先级 / 状态 /
截止 / 进度 / 标签）+ 全选 + 四列可排序 + 分组轴 + 批量条（`view.rs:1697-1778`）。

差距只在**自家设计未兑现**的部分：
- 设计 F23 写「批量：改状态 / 改优先级 / **加标签** / **归档** / 移动项目 / 删除」；
  实现只有 5 个动作（改状态 / 改优先级 / 移入项目 / 标记完成 / 删除），
  **缺加标签、缺批量归档**（`view.rs:1778-1948`）。
- 列可显隐（设计 F8）未实现：7 列固定。
- `TaskSort` 支持 6 档（手动 / 截止升降 / 优先级 / 进度 / 创建），但**没有「按标签排」**
  （内核 `TaskSort` 无此变体，属内核缺口）。

| --- | --- | --- |
| 形态 | 双栏：左日历 + 右「选中日任务清单」（`:1-140`） | 页内 6×7 月网格 / 1×7 周看板 + 右键菜单；浮窗 320×430 月历 + 底部清单（`calendar_float.rs:37`） |

结论：页内日历**不弱**（双模 + 右键 + 口径齐全），弱的是**浮窗**：参考的日历窗是
「可调、可搜、可写、带当日面板」的第二工作区，本方浮窗是「只读月历」。

### 2.7 详情

参考（弹窗，`TaskDetailModal.vue`）分区：
状态头（图标 + 状态徽标 + 一句解释）→ 标题 + 描述（Markdown 渲染）→ 进度（**滑块**，
`min` 绑当前值）→ 4 列信息网格（分类 / 四象限 / 优先级 / 标签）→ 次级信息
（**Git 分支** / 预估 / 实际）→ 时间轴（创建 / 计划开始 / 开始 / 里程碑 / **最后活跃**）
→ 里程碑内联表单（标题 / 描述 / 进度快照）→ 底部动作。

本方（右栏，`task_detail_panel.rs:53-390`）分区：
头（状态点 + 优先级 + 项目）→ 概览 → 属性（状态 / 优先级 / 四象限 / 项目 / 起止 / 工时，
**全部内联可改**）→ 进度（四档推进 25/50/75/100）→ 子任务汇总 → 里程碑（只读 + 达成
切换）→ 工作上下文（文件 / SQL / 页签）→ 描述与备注 → 底部动作。

差距：
- **进度在右栏只能四档**（`PROGRESS_STEPS`，`task_detail_panel.rs:48`），参考可连续拖；
  精确调整要开编辑器（那边有滑块）。
- **时间轴缺失**：本方只有 `created_at` / `updated_at` / `completed_at`
  （`db.rs:74-107` 的 tasks 表**无 `started_at` / `last_active_at`**），所以画不出
  参考那条「创建 → 计划开始 → 开始 → 里程碑 → 最后活跃」的轴。
- **Git 分支字段有列无界面**：`tasks.git_branch` 已加（`db.rs:237`、`models.rs:450-454`），
  但 `pages/projects` 里 **0 处引用** → 编辑器没输入框、详情没展示、卡片没有标记。
- 子任务只有汇总（`2/5`），无逐条勾选；参考同样不列明细（也是汇总），平手。
- 里程碑：本方「达成」是显式点圆点（内核存 `reached_at`），参考按 `progress >= snapshot`

## 8. 操作流程对照（补章）

前七章量的是「屏幕上有什么」。这一章量「手怎么走」：同一个意图，从产生到落地要经过几次触发、几次上下文切换、做错了有没有退路。

### 8.0 四条标尺

| 标尺 | 问法 | 为什么它比「有没有这个功能」重要 |
| --- | --- | --- |
| 触发距离 | 从「想到」到「界面有反应」，手要不要离开当前窗口 | 捕获类动作的价值全在「不打断」；多切一次窗，想法就凉了 |
| 步数 | 点击 / 按键 / 弹层计数（不含输入文字） | 高频动作每多一步，一天乘几十次 |
| 上下文切换 | 是否换视图、换窗口、换焦点 | 换一次就要重新建立「我在哪」 |
| 退路 | 做错了能不能一步回去；有没有回执 | 没有退路的快路径，用户用两次就不敢用了 |

下面 13 条通路，按一个人一天里真实发生的顺序排：捕获 → 定位 → 启动 → 推进 → 收尾 → 复盘 → 整理。

### 8.1 步数账本

| # | 通路 | 参考（devAssistant） | 本仓 | 差 | 性质 |
| --- | --- | --- | --- | --- | --- |
| T1 | 捕获一条任务 | 设计上：全局键 → quick-task 窗 → 输入 → Enter<br>实际：窗只能从主窗入口打开（**快捷键未注册**） | ⌥Space → 搜「项目」→ Enter → N → 输入 → Enter | 本仓 5 步（全键盘）；参考设计 1 键落到输入框 | 双方都缺；本仓离得近 |
| T2 | 决定这条落在哪 | 扁平任务，无项目，只有 `#标签` 与高优先级 | `@项目` > 当前范围；列底 `+` 预填状态 | **本仓领先** | 保持 |
| T3 | 缩小到今天/本周该做的 | 顶部一张筛选卡：象限 + 标签 + 结果数 + 重置 | 左栏 scope → 左栏 smart → 工具条标签 → 工具条排序 | 3 步 + 一次人眼过滤 | 结构差 |
| T4 | 启动一条 | 卡上「开始」（`TaskCard.vue:87`） | 右键 → 开始（`task_menu.rs:115-125`）；或 Enter → 右栏下拉 | +1 步 + 一次右键瞄准 | 入口位置差 |

| T9 | 周计划 | 选周 → 勾选 → AI 生成 → 润色 → 保存 → 确认 | Draft/Confirmed + `added_task_ids` + AI 生成 | 缺「上周遗留滚入」 | 缺一步关键动作 |

| T11 | 误操作回退 | 卡上动作直发事件（`emit`），无确认也无撤销实现 | ⌘Z 栈（32 步 / 60 秒 / 4 类动作） | **设计领先，覆盖不全** | 见 8.5 |

### 8.2 T1 捕获：能力已经写好，只差「离开页面也能用」

本仓的 `quickparse` 是全项目最被低估的一块（`quickparse.rs`）：`#标签`、`@项目`、`!P0`、`明天 18:00`、`下周三` 都能解析，还有 AI 兜底（`dialogs.rs` 的 `spotlight_ai_row`）。chips 实时预览也在。

问题是它**只活在项目管理页里**：

- 命令面板能跳到项目管理页（`ROUTE_PROJECTS`，`actions.rs:159-175`，`⌘6`），所以「到达页面」不是问题；问题是**没有动作条目**——面板里搜「新建任务」零结果，而「页面跳转」与「把光标放进输入框」是两件事；
- 所以「在写代码时想到一条」的路径是：切到 app → ⌥Space → 输入「项目」→ Enter（到页面）→ 按 `N`（开 Spotlight）→ 输入 → Enter。**5 步、两次 Enter、一次视图切换**，全键盘但仍有四次「我在干嘛」的重建；
- 浮窗（⌥⌘T，真注册了全局键）里那行「新增」走的是 `create(&title)`（`float.rs:445-467`），**不解析任何记号**：同样一句 `修登录 #bug 明天 18:00`，在主窗是「标签+日期」，在浮窗是「标题里带三个井号」。同一句语法，两个入口两种语义。

参考侧要公平地说一句：它设计了 quick-task 独立窗与 `Ctrl+Shift+N`，文档写得像已经能用（`docs/GLOBAL_SHORTCUT_TESTING.md`），但 `src-tauri/src/` 里**没有任何 `on_shortcut` 注册**，插件与权限是空转的。所以这不是「抄它」，是两边都没做完，而本仓缺的那一块比它小。

**最小改法（不动窗口模型）**：给 launcher 加一条动作「新建任务」（`duck_command::declare` + `ActionSlot::Palette`，处理器里 `navigate_to(PROJECTS_ROUTE)` 后立刻 `open_spotlight`），这样 `⌥Space` → 敲「新建」→ Enter → 输入 → Enter，省掉「到页面再按 N」的两步；再加一条「新建并聚焦输入」属于同一动作的顺手版本。不需要新窗口、新热键、新生命周期。浮窗那行则直接换 `quickparse::parse` + `create_task_from_quick`，与 Spotlight 同一个落库口（`state.rs:1583`）。

**→ 本轮已修**：`actions.rs` 加了 `PROJECT_NEW_TASK`（`⌘K` 搜「新建任务」直接开 Spotlight），浮窗新增改走 `quickparse::parse` + `ensure_tag` + 项目名匹配 —— 同一句 `修登录 #bug 明天 18:00` 在两个入口现在是同一个语义。

### 8.3 T3 定位：不是筛不出来，是「筛」被拆成了四个抽屉

参考把筛选收在一张卡里（象限 / 标签 / 重置 / 结果数，`TaskBoard.vue:58-99`），一次点击就能看到「还剩几条」。本仓的筛选分布在四处：

| 维度 | 在哪 | 是否参与组合 |
| --- | --- | --- |
| 范围（全部/收集箱/项目） | 左栏 | 是 |
| 智能列表（今天/本周/逾期/未排期） | 左栏 | 是 |
| 标签 | 工具条（单选） | 是 |
| 搜索词 | 左栏输入框 | 是 |
| 排序（截止/优先级/创建/标题） | 工具条 | 是（只影响顺序） |
| 四象限 / 优先级 / 多标签 | **没有** | — |

内核 `TaskQuery` 早就支持 `quadrants` / `priorities` / 多个 tag（`query.rs`），界面只接了单标签。于是「本周 + P0 + 后端」这个真实问题，走法是：点本周 → 点「后端」→ 排序切「优先级」→ **人眼在结果里挑 P0**。前两步是筛选，最后一步是体力活。

结果数也没有：参考常驻「筛选结果: N 个任务」（`TaskBoard.vue:99`），本仓只在左栏给全局计数（`SidebarCounts` 明确注释「与当前筛选无关」）。**筛选之后不知道剩几条**，用户无法判断「是我筛错了还是真没有」。

**最小改法**：工具条加一个「筛选」按钮 + 一个计数徽标，弹层里放四象限 / 优先级 / 多标签 / 重置；`query()` 里把三个新条件接上（内核已具备）；状态栏那行「N 快速新建 · ⌘N 新建任务…」的左侧加「N 条」结果计数。

**→ 本轮已修**：工具条多了「筛选」按钮（`f` 也能开），面板里三组多选 chip + 重置；`query()` 接上 `tags` / `quadrants` / `priorities`（组间 AND、组内 OR）。结果计数**本来就有**（状态栏 `本视图 {} 条` = `tasks().len()`），所以没再加第二个。

### 8.4 T6 完成：四条路径，三种反馈，两种退路

这是整份报告里最值得先修的一处。同一个「完成」意图，本仓有四条实现：

| 路径 | 调用链 | 回执 | 撤销 | 失败提示 |
| --- | --- | --- | --- | --- |
| `Space`（键盘） | `toggle_selected` → `toggle_done` → `move_task`（`mod.rs:1285`） | **无** | **无**（`move_task` 不压栈，`state.rs:1075-1083`） | 只写进 `state.error` |
| 右键「标记完成」 | `set_task_status`（`state.rs`，带 `RevertStatus`） | 有 | **有**（`RevertStatus`） | 回执里说原因 |
| 拖拽到 done 列 | `move_task_to` → `move_task`（`mod.rs` + `state.rs:1075`） | 无 | **无** | 静默 |
| 批量条「标记完成」 | `bulk_set_status`（`state.rs:1330`） | 有 | **无** | 逐条停 |

代码自己在注释里承认了这件事：`UndoAction::RevertStatus` 上写着「只有弹回执的那条路径才压它：拖拽落列走 `move_task`，那条路径不弹回执」。这不是疏忽，是一个**没被统一定义的取舍**——快路径不想打扰，于是连退路一起省了。

叠加第二个问题：**完成之后没有「下一条」的交接**。

- `reload()` 不动 `selected`，所以完成后高亮**跟着卡片跑到 done 列**（默认 `show_done = true`，`state.rs:381`；看板默认列含 done）；
- 用户此时的自然动作是再按一次 `Space` 继续下一条——但 `toggle_done` 对 `Done` 的定义是「退回 todo」，于是**刚完成的那条被原地撤回**（`toggling_done_bounces_between_done_and_todo` 钉住语义，`state.rs:2790`）；
- 若关掉「显示已完成」：卡片当场消失，`selected` 指向一条不在 `self.tasks` 里的 id，再按 `Space` 在 `toggle_done` 里找不到它、**直接 return**（`state.rs:1482-1489`）——按键有反馈感，但什么都没发生。

两种模式各错一半：一个误退，一个卡住。根因是同一个：**完成之后没有「下一条」的交接**。

**最小改法（两处，都很小）**：
1. `move_task` 里补 `push_undo(RevertStatus { 旧状态 })`（它已经知道 id，只需在写库前读一次旧状态）；回执仍然只在菜单路径弹，避免键盘连打时提示条刷屏。
2. `toggle_selected` 完成之后调一次 `select_next(1)`（仅当新状态是 `Done`）；「重新打开」保留给右键菜单与 ⌘Z。

**→ 本轮已修**：① `move_task` 写库前读旧状态并压 `RevertStatus`，拖拽与 `Space` 从此都有退路；② 新增 `state::select_next_open(order, done_id)` —— 沿 `movement_order()`（看板=列序、列表=行序）往后找第一条 `!= Done`，走到头再往前，全没了就 `selected = None`。**没有直接用 `select_next(1)`**：`show_done = true` 时「下一条」在视觉上就是 done 列里那张卡，前移一格会落到刚完成的那条上。三条单测钉住：移到下一条、完成最后一条清空选中、跨列移动留撤销。

### 8.5 T11 退路：撤销栈的「承诺面」比「实现面」大

撤销栈本身设计得比参考好：32 步、60 秒、带 `seq` 防止定时器互相踩（`state.rs:176-215`）。但 `UndoAction` 只有四类：归档任务、归档项目、改状态（菜单路径）、复制任务。

用户学到的是「⌘Z 能退」，实际退不了的是：

- 拖错列（最高频的误操作）；
- `Space` 完成（第二高频）；
- 批量改状态 / 批量改优先级 / 批量移项目（一次错一片）；
- 批量删除（虽有二次确认，但确认之后没有任何退路）；
- 编辑弹窗里的字段改动（`UndoAction` 里根本没有「改字段」这一类；`dialogs.rs:187` 也在同一处提醒「弹窗里没有撤销」）。

**最小改法**：`bulk_*` 三个方法各压一条「批」撤销槽（记录 `Vec<(id, 旧值)>`），比逐条压栈更省；`move_task` 同 8.4。

**→ 本轮已修**：`UndoAction` 从 `Copy` 降为 `Clone` 并新增两档 `BatchedStatus(Vec<(i64, TaskStatus)>)` / `BatchedFields(Vec<BatchedField>)`；`bulk_set_status` / `bulk_patch` 写库前收集旧值、只压**一条**批槽（连按 `⌘Z` 不会一次退一条）；`forget_undo_for_tasks` 换成 `UndoAction::mentions(&ids)`，删掉的任务不会在批槽里留下半截。

### 8.6 T8/T9 收尾与复盘：链路都在，缺「交接动作」

本仓的日志链路其实比参考细：草稿按「这一天 + 这一档」认领（`dialogs.rs:2946-2953`）、`ai_generated` 来源标记、AI 素材固定为「打开弹窗那一刻的全量顶层任务」（`dialogs.rs:1037-1055`，注释解释了为什么不用当前筛选）。周计划有 Draft/Confirmed 与 `added_task_ids`，能说出「其中 3 项是后来加的」——这是参考没有的。

缺的是流程上的两个交接：

1. **完成 → 写日志** 之间没有钩子。一天做完 6 条，没有任何时机提示「该写日报了」；用户要自己想起切到视图 6。参考也没有这个钩子，但它有通知中心可以承载（本仓没有）。
2. **周与周之间没有交接**。全仓搜「顺延 / 滚入 / rollover」零命中。周一早上第一件事是手工把上周未完成逐条改日期——而这件事内核一条 `bulk_patch(due)` 就能做。

**最小改法**：① 状态栏在「今天完成数 ≥ 3 且今天还没有日志」时显示一句轻提示（不是弹窗，不打断）；② 周计划面板加一个「带入上周未完成」，走 `bulk_patch` + 一条撤销槽。

**本轮落地情况**：① 已做 —— 状态栏那枚 chip（`今天已完成 N 条 · 写日报`，点了直接开今天的日报），两个数由 `state::refresh_log_hint` 在每次 `reload()` 里重算（一个 `COUNT` + 一次当日日志区间，读失败按「已写过」处理，绝不为了提示弹错）。② 做了「带进这一周的计划」，**没做**「顺延截止日」：后者要先定义「顺延到哪天」，而这一条没有共识之前，改日期比不改更糟（见 §8.13 第 8 条）。

### 8.7 T7/T12 跨窗：三个窗口，三套写权限

| 能力 | 主窗 | 随手看（⌥⌘T） | 日历浮窗（⌥⌘C） |
| --- | --- | --- | --- |
| 看列表 | ✅ | ✅（进行中 + 待办前 5） | ✅（月格 + 当日清单） |
| 改状态 | ✅ | ✅（开始/暂停/完成/返回） | ❌ 只读（模块头第 3 条） |
| 新增 | ✅（Spotlight 解析） | ✅（纯标题，不解析） | ❌ |
| 完整编辑 | ✅ | ❌（有意） | ❌ |
| 批量 | ✅（仅列表视图） | ❌ | ❌ |

权限分档本身是合理设计（小窗不该养一套回执）。问题在**接力的最后一步**：浮窗底部「主窗口」按钮只做 `reveal_main_window` + `navigate_to(PROJECTS_ROUTE)`（`float.rs:1068-1082`），**不带当前展开那条的 id**。于是「在小窗看到一条 → 想深入 → 点主窗口」的结果是：落在一屏全量看板，重新找。注释写的是「目的就是看那一条」，实现没做到。

参考在这件事上是做对的：浮窗编辑时把 300×550 临时放大到表单尺寸，编完恢复（`TaskFloatApp.vue` 的 `expandWindow` / `restoreWindow`）——窗口尺寸是流动的，不是硬边界。

**最小改法**：`navigate_to` 之外加一个「待选中任务」的载荷（或给 `app` 一个 `reveal_task(id)`），浮窗按钮传 `expandedTaskId`；主窗进来先 `select_task(Some(id))` 并 `reveal_right_dock`。参考的「放大窗口」不必抄——那是另一条路（窗口尺寸流动 vs 上下文传递），本仓已有右栏，传 id 更省。

**→ 本轮已修**：走的是「总线带载荷」这条路 —— 新增 `bus::FocusTask(i64)` 事件（与空载荷的 `ProjectChanged` 分开：一个说「重读」，一个说「定位到这条」），浮窗「主窗口」按钮先取当前展开那条的 id，`reveal_main_window` → `navigate_to` → `bus::focus_task` → 隐藏；页面订阅后 `select(Some(id))` + `set_right_sidebar_open(true)`。

另有一个具体摩擦：浮窗「不抢焦点」⇒ **`Esc` 收不起来**（`float.rs` 模块头第 1 条自己写明），收起只有「再按一次全局键」或「点 ✕」。键盘用户从浮窗回到工作，要按两次 ⌥⌘T。

### 8.8 T13 提醒：只广播，不接单

`remind.rs` 的策略是克制的：天级事实、5 分钟一轮、一天只说一次、单轮最多 3 条其余折成汇总、逾期太久直接不提。这套「不刷屏」的判断比多数产品成熟。

但它只是**广播**：

- ~~没有通知中心，历史无处回看~~ —— **这一句是错的**（本轮复核）：`duck-components/src/notify.rs` 本来就有 `history` / `unread_count` / `mark_history_read` / `remove_from_history` / `clear_history`，上限 `HISTORY_LIMIT = 100` 的环形缓冲，落 `kv`；shell 层的通知面板读的就是它。缺的从来不是存储，是**入口的显眼程度**。
- 通知横幅不带动作（`mod.rs:58` 注释：`notify` 没暴露 `Notification::action`），所以看到「今天到期：登录超时」之后，唯一能做的是自己开窗找那条 —— **本轮已补**：`notify::system_with_toast_action` + `notify::BannerAction`，提醒横幅上多一个「完成」，点了真落库（`set_task_status`）并广播 `ProjectChanged`，打开着的页面/浮窗各自重读；
- 时刻不参与（`due_time` 不进扫描，天级比较），所以「18:00 开会」不会在 17:30 响。

**剩余**：第二个动作「明天」没做 —— 它要回答「明天是几号」之外的问题：顺延到明天早上几点？傍晚？不定义这个，按下去只会把日期改成「明天」而时刻留空，等于把用户的时间承诺悄悄降级。这是产品决定，不该由实现顺手拍。

**最小改法（已落地的那一半）**：`duck_components::notify` 补 `action` + `BannerAction`（`Rc<dyn Fn>`，因为上游 `Notification::action` 的闭包是 `Fn`、每帧重跑）；注意上游 `action` 会**关掉 `autohide`** —— 有按钮的通知要等用户表态，对「到期提醒」正好。

### 8.9 T4/T5 启动与进展：`started_at` 不是「番茄钟的前置」，是「流程的前置」

现在「开始」只是一个状态位。没有 `started_at` / `last_active_at`（`db.rs` 的表里就没有这两列），带来三个流程后果：

1. 开始之后**看不见「从几点开始」**——浮窗展开详情里只有标题、描述、分支、到期，参考的浮窗会显示「开始: 10:32」（`TaskFloatApp.vue:40-43`）；
2. 「暂停」与「从没开始过」在数据上无法区分，于是「这条放了三天」只能靠 `updated_at` 粗判；
3. 报表里的工时/节奏维度无从算起（已在旧清单 G-PRJ-18）。

记录进展也一样：`progress` 字段有、进度条组件有，但**没有「记一次」的入口**——只能开编辑器改数字（4 步）。参考在卡上直接显示 `<n-progress>` 并在详情里给滑块（`TaskCard.vue:49-68`）。另外参考卡片菜单里挂着「开始番茄钟」（`handleStartPomodoro`，`TaskCard.vue:239`），完成时会顺带停下计时——这条闭环本仓完全没有，因为计时本身不存在。

**最小改法**：`move_task` 迁移到 `Doing` 时写 `started_at`（若为空），任何写动作更新 `last_active_at`；浮窗详情加一行「开始 10:32 · 已 2 小时」；卡片右键加「进度…」子菜单（25/50/75/100 四档），比滑块省一层。

### 8.10 T10 批量：只在列表，且退不回

批量条本身做得不错：改状态 / 改优先级 / 移项目 / 标记完成 / 删除（二次确认）/ 取消选择，且走与单条同一个内核入口（`bulk_set_status` 注释解释了为什么不另写一条 SQL）。

但入口只有一处：勾选框在**列表行**上（`view.rs:1962-2046`），看板卡片没有（`task_card.rs` 里 `checked` 零命中）。于是「在板上一眼看出来 5 条该归到一个项目」这件事，要先切到列表（按 `2`）→ 逐条勾 → 批量改 → 再切回看板（按 `1`）。三步上下文切换，只为了一次批量。

**最小改法**：卡片左上角加勾选框（悬停显示，选中态常显），选中数与批量条逻辑复用；批量动作统一压一条「批」撤销槽（见 8.5）。

**→ 本轮已修**：`task_card` 收一个 `checked: bool`，`.ctop` 行最左插与列表同一个 `check_box`（`view::check_box` 提成 `pub(crate)`，两处共用一份外观与点击语义）；`kanban_column` 逐卡传 `checked.contains(&task.id)`，勾选状态与批量条、`Esc` 取消选择全部同源。

### 8.11 键盘：覆盖了「选与切」，没覆盖「筛与建」

现有 **13 个动作 / 19 条绑定**（`mod.rs:220-248`；`1`–`6` 各占一条），这套设计比参考完整（参考没有页面内键盘流）：

| 已有 | 语义 |
| --- | --- |
| `N` / `⌘N` | 快速新建 / 完整新建 |
| `J` `K` | 上下移动选中（看板按**列序**走，有测试钉住 `state.rs:2734`） |
| `Space` | 完成 / 取消完成 |
| `Enter` / `E` | 右栏详情 / 编辑弹窗 |
| `A` / `⇧A` / `Esc` | 归档 / 归档中心 / 返回 |
| `1`–`6` | 六视图切换 |
| `⌘Z` | 撤销 |

缺的四条（按价值排）：`/` 聚焦搜索（现在要鼠标点左栏输入框）、`f` 打开筛选（见 8.3）、`?` 快捷键帮助（12 条已经记不住了）、`g` 切分组。**前两条本轮已落地**（`FocusSearch` / `ToggleFilters`，都是 `Projects && !Input` 的裸键）；`?` 与 `g` 仍未做 —— `?` 需要先有一份「键位表」的单一真源（现在散在 `bind_keys` 与状态栏那句提示里两处，做帮助面板前该先合并）。`Space = 完成` 与主流任务工具一致，**别改**；要改的是完成后的交接（8.4）。

顺带一个正确性说明：`select_next` 在看板下是 `columns.flat_map(tasks_in_status)`（`state.rs:1037-1047`），即**列序**，与视觉一致；不是扁平顺序。这一点没有坑，不用动。

### 8.12 三条流程反模式（比单条差距更值得记）

1. **一个意图，多条路径，后果不同**（完成 ×4、改状态 ×3）。用户学不会「按哪个」，只能学会「按哪个最安全」——而最安全的那个通常最慢。
2. **快路径绕过退路**。为了让键盘流「不被打扰」，把回执和撤销一起省了；结果快路径变成「不敢用」。
3. **能力挂在窗口上，而不是挂在对象上**。同一条任务，在主窗能编辑、在随手看能改状态、在日历窗只能看。用户要维护一张「哪个窗能做什么」的心智表——而这张表没有任何地方写着。

### 8.14 本轮修完之后仍然存在的三条（判据 + 为什么没修）

1. **「完成」仍有四条路径**（卡片勾选框 / 菜单 / `Space` / 批量条），四条现在都进撤销栈、都会把选中前移，但**回执文案仍有两种**（批量说「已把 N 条标记为完成」，单条说「已完成」）。要不要合并成一句，是个文案决定，不是缺陷。
2. **`started_at` / `last_active_at` 仍不存在**（§8.9）。这一条牵 `db.rs` 加列 + 全仓下标扫（`docs/projects-design.md` 的迁移纪律），不该混在流程批次里做；而且没有番茄钟时它的唯一用途是浮窗一行「开始 10:32」，收益小于风险。
3. **浮窗 `Esc` 收不起来**（§8.7 末尾）。浮窗刻意不抢焦点，`Esc` 就到不了它手里 —— 这是设计代价，不是漏绑。真要收，只能靠全局键或点 ✕。
